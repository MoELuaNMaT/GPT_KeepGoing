# 自动续跑助手（Auto Resume）— 设计规格

状态：MVP 已实现 v0.2
更新日期：2026-10-26
适用范围：本机 ChatGPT（Codex）Windows 桌面客户端的对话状态读取与自动继续

---

## 1. 背景

目标客户端是 MSIX 包 OpenAI.Codex，Electron / Chromium 架构。今天在这台机器上实测到四条事实：

1. **客户端不自动刷新额度状态。** 19:33–19:41 共 24 次采样，窗口全程未激活，跨过 19:37 重置点后，界面仍显示「额度已用完」，一次未变。
2. **置前也不刷新。** 把窗口恢复并拉到前台 2.5 秒，状态不变；打开模型选择面板也不变。
3. **切换对话会触发重新取数。** 切走再切回后，横幅文案从「或在 19:37后重试」变成「或稍后再试」，重置时刻与按钮消失。
4. **到点不等于可用。** 19:46 重新取数后仍报「已达使用上限，请稍后再试」，且不再给出重置时间。

后果：额度恢复后，用户必须手动回到对话、手动点「恢复目标」或输入「继续」。夜间恢复的额度会一直闲置。

---

## 2. 目标

做一个独立的 Windows 桌面小应用，满足：

- 自动找到本机正在运行的 ChatGPT 客户端。
- 读取并展示一个**锁定对话**的状态。
- 提供「自动继续」开关。开启后每分钟检查一次。
- 额度用尽时，在重置时刻自动执行一次继续动作。
- 任务执行中时，任务结束后自动补一次继续。
- 提供带时间戳的执行日志。
- 全程可在仪表盘看到发生了什么。

## 3. 非目标

- 不修改客户端、不注入代码、不改配置、不代理网络。
- 不调用 OpenAI API，不读取账号凭据。
- 不做多对话并发管理（后续）。
- 不做开机自启（后续）。
- 不自动批准权限申请。

---

## 4. 术语

| 术语 | 含义 |
| --- | --- |
| 锁定对话 | 开启开关那一刻客户端里打开的对话，用（项目名，对话标题）标识 |
| 陈旧（stale） | 界面显示的状态与真实状态不一致。判据见 FR-7 |
| 刷新阶梯 | 一组由轻到重、用来强制客户端重新取数的界面操作 |
| 续跑 | 自动发起一次「继续」，形式为点恢复目标或发送「继续」 |
| 硬封锁 | 额度耗尽到发送按钮整个消失的状态 |

## 5. 功能需求

### FR-1 客户端发现

- 按进程名 `ChatGPT.exe` 与窗口类 `Chrome_WidgetWin_1` 找主窗口。
- 找不到时状态置 `app_missing`，每 10 秒重试，不弹错误框。
- 找到多个窗口时，取有标题且面积最大的一个。

### FR-2 锁定对话

- 开启开关时记录当前 `(项目, 对话标题)`。
- 关闭开关不清除锁定。再次开启时重新锁定当时打开的对话。
- 锁定对话被归档或删除时，状态置 `locked_thread_missing`，停手并通知。

### FR-3 状态读取

- 单次读取产出：项目、对话标题、模型、权限、上下文用量、额度状态、重置时刻、目标状态、输入框是否为空、发送按钮是否可用。
- 状态枚举与优先级：`running` > `needs_permission` > `needs_reply` > `quota_exhausted` > `idle`。
- 额外状态：`app_missing`、`locked_thread_missing`、`stale`。
- 读取不抢焦点，不改变界面。
- 「需要用户回复」只认客户端自己的活动状态行（以「正在等待你的回答」开头），
  且该行必须当前可见。禁止用包含匹配：消息正文里出现「请选择」之类的词会造成误判。
- 「需要权限」只认审批卡上的按钮名，不认正文。
- 「额度用尽」的横幅同样必须当前可见才计数。残余风险见 §11。

### FR-4 仪表盘

必须显示：

| 字段 | 说明 |
| --- | --- |
| 锁定对话 | 项目名 + 对话标题 |
| 当前状态 | 状态徽标 + 一句中文说明 |
| 额度重置时刻 | 有则显示 `HH:MM` 与本地日期时间；无则显示「客户端未给出重置时间」 |
| 倒计时 | 距重置时刻还有多久 |
| 自动继续开关 | 开 / 关 |
| 执行日志 | 列表，每行带时间 |

若客户端当前打开的不是锁定对话，显示一行提示：「当前打开的是『X』，执行时会切回锁定对话」。

### FR-5 开关与确认弹窗

- 关闭 → 开启时，必须先弹模态确认框，用户点确认后才真正开启。
- 弹窗必须说明三件事：① 客户端不会自动刷新；② 因此执行时会把窗口强制显示到前台；③ 这会打断当前操作。
- 文案见 §8。
- 取消则开关保持关闭。

### FR-6 轮询

- 开启后每 60 秒读取一次。
- 读取在后台线程执行，不阻塞界面。
- 关闭后仍然每 60 秒读取一次，但只用于界面展示，不参与决策、不动作、不切换对话。
  这样用户一打开应用就能看到当前对话和状态。

### FR-7 陈旧判定与刷新阶梯

满足任一条即判定陈旧：

- 当前时间已过重置时刻 90 秒，但仍 `quota_exhausted`。
- 状态从 `quota_exhausted` 变为非该状态，但发送按钮仍不可用。
- 重置时刻与上一次记录不同。

刷新阶梯，每级执行后等 3 秒重读，成功即停：

| 级 | 动作 | 代价 |
| --- | --- | --- |
| L0 | 直接读取 | 无 |
| L1 | 切到相邻对话，再切回锁定对话 | 视图闪动 |
| L2 | 发送 Ctrl+R 重载页面 | 丢失草稿与滚动位置，需先确认输入框为空 |
| L3 | 重启客户端进程 | 最重。**MVP 不实现**，L1/L2 都失败时直接转人工通知 |

执行任何继续动作之前，必须先走到 L0 或 L1 成功。

### FR-8 到点执行

前置条件：

1. **额度**：未过重置时刻时，横幅显示用尽就不执行；**过了重置时刻就尝试**，
   哪怕横幅仍显示用尽。横幅已知会滞留，成功与否以动作之后的状态为准。
2. 输入框为空（有草稿则不执行，见 §11）。
3. 锁定对话已在前台。

> 这条是实际故障倒逼出来的：2026-10-27 00:45 额度重置后，横幅仍写着
> 「你已达到使用上限…或稍后再试」，旧实现据此判定"额度仍显示用尽"直接返回，
> 从未点击。修复后同一场景点击成功，状态转为运行中。

执行方式按优先级：

| 条件 | 动作 |
| --- | --- |
| 有目标，且目标状态为「目标已停滞」或「已暂停的目标」 | 点「恢复目标」；若弹出「恢复已暂停的目标吗？」再点「继续目标」 |
| 有目标，且目标状态为「进行中的目标」 | 不动作，视为已在运行 |
| 有目标，且目标状态为「已达成目标」 | 不动作，通知用户 |
| 无目标 | 聚焦输入框 → 清空 → 粘贴「继续」→ 点「发送」 |

动作后进入 90 秒冷却，冷却结束再判成败：状态变为 `running` 视为成功。

### FR-9 到点仍不可用

- 每次在被滞留横幅挡住却仍然尝试时，写一条 `act_stale_banner` 日志以便追溯。

- 触发后 10 分钟内，每分钟重试一次，共最多 10 次。
- 每次重试前先走刷新阶梯。
- 全部失败 → 停止自动执行，状态置 `needs_human`，发一条通知。
- 通知内容包含最后读到的额度文案。

### FR-10 任务结束后续跑

- 状态从 `running` 变为 `idle` 且开关开启 → 按 FR-8 的动作表执行。
- 状态从 `running` 变为 `needs_permission` 或 `needs_reply` → 不执行，只通知。
- 续跑次数不设上限，直到用户关闭开关。

### FR-11 额度提前恢复

- 若在等待期间检测到额度已恢复且状态为 `idle`，立即执行，不必等到定时。
- 该行为写入日志，注明「提前恢复」。

### FR-12 权限申请

- 状态为 `needs_permission` 时，不点任何审批按钮。
- 只发一次通知，同一对话同一次申请不重复通知。

### FR-13 日志

- 每次读取、每次决策、每次动作、每次失败各写一行 JSONL。
- 每行必须含本地时间（ISO 8601，带时区偏移）。
- 日志按天分文件，保留 30 天。

### FR-14 通知

- 用托盘气泡通知，不弹模态框。
- 只在三种情况通知：进入 `needs_human`、到达重试上限失败、锁定对话丢失。

### FR-15 单实例

- 用命名互斥体保证只跑一个实例。重复启动时把已有窗口提到前台。

### FR-16 托盘

- 托盘常驻一个图标，提示文字显示当前状态与目标对话。
- 双击图标或菜单「显示仪表盘」还原窗口。
- 关闭窗口时收进托盘，不退出进程；退出走菜单「退出」。
- 菜单项：显示仪表盘 / 立即续跑 / 退出。

### FR-17 立即续跑

- 仪表盘提供「立即续跑」按钮，跳过定时立刻执行一次。
- 前置校验与 FR-8 相同。
- 手动触发不计入 FR-9 的 10 次重试窗口。

### FR-18 最近日志

- 仪表盘日志区只显示最近 20 条，每条含时间、事件、结果。
- 完整日志仍在 JSONL 文件里，用「打开日志目录」查看。

### FR-19 目标对话与多会话

- 目标对话有两种来源：锁定当前打开的对话，或从会话列表中选择。
- 会话列表从侧边栏读取，按「项目 → 对话」分组。
- 「跟随当前打开的对话」开关：开启后每轮把目标更新为当时打开的对话。
- 打开的不是目标对话时，状态显示「目标对话未打开」，且**不把当前对话的状态算到目标上**，也不动作。
- 到点执行前切回目标对话。

### FR-20 开机自启

- 写当前用户注册表启动项 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值名 `AutoResume`。
- 勾选即时生效，取消即时删除。
- 需要管理员权限时不做，只提示。

### FR-21 多语言

- 界面右上角有「语言」按钮，点开是小弹窗，内含下拉菜单。
- 支持：简体中文、English、日本語、한국어、Deutsch、Français、Italiano。
- 下拉列表里的语言名一律用该语言自己的文字书写。
- 切换语言同时改变三样东西：窗口标题、全部界面文案、发给对话的继续用语。
- 继续用语按目标语言的习惯表达，例如 继续 / Continue / 続けて / 계속 진행해 / Weiter / Continue / Continua。
- 语言选择写入配置，重启后保持。

### FR-24 目标状态识别

客户端目标条共六种文案：进行中的目标、已暂停的目标、目标已停滞、已达成目标、
目标受限、目标使用受限。归一成以下模式：

| 模式 | 判定 | 行为 |
| --- | --- | --- |
| active | 进行中的目标 | 继续监控，不动作 |
| paused | 已暂停的目标 | 维持原行为：到点或任务结束后点恢复 |
| blocked_by_quota | 目标已停滞，且当前额度用尽 | 维持原行为：等额度恢复后点恢复 |
| blocked | 目标已停滞，但额度正常、对话空闲 | 记录时间、通知一次、关闭自动继续 |
| completed | 已达成目标 | 记录时间、通知一次、关闭自动继续 |
| limited | 目标受限 / 目标使用受限 | 不点恢复，通知 |

**关键区分**：`目标已停滞` 有两种成因。因额度用尽导致的停滞可以救，必须继续等；
只有额度正常时仍停滞，才是 agent 自己放弃。二者不能混为一谈。

进入 blocked / completed 后：写 `goal_terminal` 日志（含时间）、发一次通知、
把自动继续关掉，即结束该对话的监控。用户再打开开关不会重复通知，但目标仍处于
终态时不会动手。

### FR-22 余额显示

- 界面显示 5 小时窗口与每周窗口的剩余百分比、重置时间。
- 重置时间有两种来源，优先级如下：
  1. 界面横幅（最新、最准）。客户端会写成 `19:37`、`2026年10月27日 00:45`、
     `10月27日 0:45` 等多种格式，解析器都要支持。
  2. 本地会话记录的 `resets_at`。
- 百分比只能来自本地会话记录。**只有当记录的窗口与横幅的窗口一致（相差 ≤2 分钟）
  才显示百分比**，否则显示「百分比待更新」，绝不把旧窗口的数字套到新窗口上。
- 同时显示数据时间与距今多久。
- 若当前时间已过该窗口的重置时间，显示「已过重置时间，等待新数据」。
- 剩余 ≤30% 显示橙色，≤10% 显示红色；百分比未知时用灰色。

### FR-23 通知

- 沿用托盘气泡，Windows 10/11 会显示在通知中心。
- 只在三种情况通知：进入 `needs_human`、重试耗尽、目标对话丢失。

## 6. 状态机

| 状态 | 进入条件 | 周期动作 | 出口 |
| --- | --- | --- | --- |
| `OFF` | 开关关闭 | 无 | 用户开启 → `MONITORING` |
| `MONITORING` | 开关开启且空闲或运行中 | 每 60 秒读一次 | 见下表 |
| `WAIT_RESET` | 读到额度用尽且有重置时刻 | 定时唤醒 | 到点 → `REFRESHING` |
| `WAIT_UNKNOWN` | 额度用尽但没有重置时刻 | 每 60 秒读一次 | 恢复 → `ACTING` |
| `REFRESHING` | 已到点 | 走刷新阶梯 | 成功 → `ACTING`；失败 10 次 → `NEEDS_HUMAN` |
| `ACTING` | 前置条件满足 | 执行一次动作 | → `COOLDOWN` |
| `COOLDOWN` | 动作后 90 秒内 | 无 | 成功 → `MONITORING`；失败 → 回 `REFRESHING` |
| `NEEDS_HUMAN` | 审批卡、提问、重试耗尽 | 无 | 用户处理或关闭开关 |
| `APP_MISSING` | 找不到窗口 | 每 10 秒重试 | 找到 → `MONITORING` |
| `LOCKED_NOT_OPEN` | 目标对话不是当前打开的那个 | 每 60 秒重读 | 目标被打开 → `MONITORING`；到点 → 先切回再执行 |

`MONITORING` 的转移：

| 读到的状态 | 下一状态 |
| --- | --- |
| `quota_exhausted` 且有重置时刻 | `WAIT_RESET` |
| `quota_exhausted` 且无重置时刻 | `WAIT_UNKNOWN` |
| `running` | 留在 `MONITORING` |
| `needs_permission` / `needs_reply` | `NEEDS_HUMAN` |
| `idle`，且上一轮是 `running` | `ACTING` |
| `idle`，其余情况 | 留在 `MONITORING` |

## 7. 已确认决策

| 编号 | 决策 | 结论 |
| --- | --- | --- |
| D-1 | 是否允许抢焦点 | 允许。执行时把窗口拉到前台 |
| D-2 | 执行时对话被切走 | 切回锁定对话再执行 |
| D-3 | 审批卡 | 只通知，不代点 |
| D-4 | 续跑次数上限 | 无上限，直到用户关闭开关 |

| D-6 | 应用形态 | 独立 Windows 桌面应用，单进程，无服务端 |
| D-7 | 技术栈 | 尽可能轻量，见 §12 |
| D-8 | 首次开启 | 必须弹确认框，说明会强制前台显示并打断操作 |
| D-9 | 开机自启、多对话 | 本版不做 |

## 8. 界面规格

单窗口仪表盘，默认 460×420，最小 420×360，可缩放。

| 区域 | 内容 |
| --- | --- |
| 顶部 | 锁定对话：项目名 / 对话标题 |
| 第二行 | 状态徽标 + 说明文字 |
| 第三行 | 额度重置：`HH:MM`（本地 2026-10-26 19:37），倒计时 00:12:31 |
| 第四行 | 自动继续：开关 + 状态说明（未开启 / 监控中 / 等待重置 / 执行中） |
| 第五行 | 当前打开的不是锁定对话时的提示条 |
| 主体 | 日志列表：时间 / 事件 / 结果。最近 200 条，可滚动 |
| 底部 | 按钮：立即检查、打开日志目录 |

状态徽标颜色：运行中蓝、额度用尽橙、待处理红、空闲灰、应用未运行深灰。

确认弹窗（开关由关转开时）：

- 标题：开启自动继续
- 正文：
  - 本应用会每分钟读取一次对话状态。
  - ChatGPT 客户端不会自己刷新额度，所以到点时必须把窗口强制显示到前台，才能确认额度已恢复。
  - 这一步会打断你正在进行的操作。
- 按钮：取消 / 我已知晓，开启

## 9. 数据与配置

配置路径：`%LOCALAPPDATA%\AutoResume\config.json`

```json
{
  "poll_seconds": 60,
  "auto_resume": false,
  "locked_thread": { "project": "SC2_REA", "title": "统筹 SC2 单位移动系统逆向" },
  "retry_window_minutes": 10,
  "cooldown_seconds": 90,
  "stale_grace_seconds": 90,
  "log_retention_days": 30,
  "continue_text": "继续",
  "language": "zh-CN",
  "follow_open_thread": false,
  "autostart": false,
  "notify_enabled": true
}
```

日志路径：`%LOCALAPPDATA%\AutoResume\logs\YYYY-MM-DD.jsonl`

```json
{"ts":"2026-10-26T19:33:01+08:00","level":"info","event":"poll","thread":"统筹 SC2 单位移动系统逆向","state":"quota_exhausted","reset":"19:37","reset_at":"2026-10-26T19:37:00+08:00"}
{"ts":"2026-10-26T19:37:31+08:00","level":"warn","event":"refresh","level_detail":"L1","result":"ok","state":"quota_exhausted"}
{"ts":"2026-10-26T19:38:31+08:00","level":"error","event":"retry_exhausted","attempts":10,"last_banner":"你已达到使用上限。升级套餐或充值额度以继续，或稍后再试。"}
```

## 10. 非功能需求

| 项 | 要求 |

## 11. 失败与边界

| 场景 | 行为 |
| --- | --- |
| 客户端未启动 | `app_missing`，每 10 秒重试，不通知 |
| 锁定对话被归档 | `locked_thread_missing`，停手并通知 |
| 输入框有草稿 | 不覆盖、不发送，写日志并跳过本次，等下一分钟 |
| 发送按钮不存在（硬封锁） | 先走刷新阶梯；仍不存在则计入重试次数 |
| 弹出「恢复已暂停的目标吗？」 | 点「继续目标」；若只有「保持已暂停」，视为失败 |
| 读取超时或元素失效 | 重读一次；连续 3 次失败置 `needs_human` |
| 客户端被最小化 | 先恢复窗口，再执行 |
| 系统睡眠跨过定时点 | 唤醒后按墙钟判断，立即执行 |
| 多显示器 / 高 DPI | 只用 UIA 控件名与 Invoke，不用坐标点击 |
| 用户手动关掉开关 | 立即停止，保留锁定对话与日志 |

## 12. 技术选型

### 推荐：Python 3.13 + tkinter + uiautomation + PyInstaller

| 理由 | 说明 |
| --- | --- |
| 已验证 | 状态读取、输入、点击、会话切换今天全部实测通过 |
| 零运行时依赖 | PyInstaller 打包成单个 exe，约 15–20MB |
| 无重框架 | tkinter 是标准库；无 Electron、无 Node、无 Web 服务、无数据库 |
| 依赖极少 | 仅 uiautomation、psutil、comtypes |

代价：启动约 1–2 秒；UIA 读取比原生慢，必须按 §10 做定向查找优化。

### 备选：C# .NET 8 + WinForms

优点：原生 UIA 更快、exe 更小、启动 < 0.5 秒。
代价：需重写已验证的读取逻辑；若做自包含发布体积约 70MB，做框架依赖发布则目标机需 .NET Desktop Runtime。

当前选择推荐方案。理由是把已验证的能力直接产品化，风险最低。

## 13. 验收标准

| 编号 | 标准 |
| --- | --- |
| AC-1 | 客户端未激活且额度用尽时，仪表盘在 60 秒内显示 `quota_exhausted` 与重置时刻 |
| AC-2 | 点开关出现确认弹窗；取消后开关保持关闭；确认后才变为开启 |
| AC-3 | 到点后若额度已恢复，10 分钟内完成一次续跑，日志含 `event=act` 与结果 |
| AC-4 | 到点后仍不可用，10 分钟内重试 10 次，然后状态变为 `needs_human` 并通知 |
| AC-5 | 无目标时发送「继续」后，5 秒内状态变为 `running` |
| AC-6 | 有目标时点「恢复目标」成功，不发送「继续」 |
| AC-7 | 出现审批卡时不点任何按钮，只通知一次 |
| AC-8 | 执行前若当前打开的是别的对话，自动切回锁定对话 |
| AC-9 | 输入框有草稿时不发送，日志记录跳过原因 |
| AC-10 | 连续运行 24 小时，内存增长 < 20MB |

## 14. 测试计划

**单元测试**（纯函数，不碰界面）

- 重置时刻解析：`19:37` → 当天；已过点 → 次日；无时刻 → 返回空。
- 状态优先级：构造组合输入，验证 running 压过 quota。
- 决策函数：喂入（状态, 时间, 配置）序列，验证下一状态与是否该动作。

**集成测试**（假读取器 + 真调度器）

- 用脚本化的状态序列模拟：用尽 → 到点 → 恢复 → 执行成功。
- 模拟：用尽 → 到点 → 10 次失败 → 通知。
- 模拟：running → idle → 续跑。

**手工验证**

- 真机开启开关，确认弹窗与前台打断行为符合预期。
- 关闭客户端，确认 `app_missing` 与自动重连。
- 手动切走对话，确认执行时切回。
